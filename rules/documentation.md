# 文档规范

## 最小化历史

**正式文档以当前有效状态为中心，尽量不让读者依赖项目的演变过程。**

- 直接维护现有内容：概念、机制或结论变化时更新原文，清理过时、重复的描述。
- 普通调参、重构、修复及方案迭代由 Git 记录；不为其额外编写过程回顾、变更流水账或旧方案叙述。
- 正式内容应自包含，不要求读者查阅旧提交、聊天记录或 Draft 才能理解。
- **保留研究证据**：具有长期比较价值的实验条件、原始数据、结果及必要的代码版本信息可以长期保存；这与记录开发历史不同。

## 表述

- **简洁**：只写有助于理解或执行的内容，避免重复、空泛解释和不必要的背景。
- **不确定方向保留模糊表述**：尚未确定的研究方向、概念、机制或计划只作概括描述；不主动补写具体方案、测试要求或评价标准。
- **准确**：区分已确认的信息、当前实现、实验观察与尚未验证的想法。需要精确定义而信息不足时，先询问。
- **减少不必要的负面表述**：优先直接说明目标、事实与做法；必要的禁止事项、真实限制和证据边界仍须明确。

## 组织

- 按**作用对象**划分规范文件（例如文档、实验、Draft）；单个规范文件内部按**规则的性质**分块，而非再按其作用对象分章。
- 普通文档记录研究模型、已形成的认识与参考资料；规范记录应遵守的要求。实验说明与数据跟随相应实验，基础设施文档由对应仓库维护。
- 临时材料遵守 [Draft 隔离规则](drafts.md)。
