# M1：真实对话中的门控分布与零证据检索（独立研究 Draft）

> 基于本机运行的 M1 实例：25 轮真实对话的 trace，加上直接调用检索函数的复现。不改 M1 公式，不改参数，只记录观测量。

## 结论

1. **门控在真实对话里一半时间是打开的**：25 轮中 12 轮 γ>0，均值 0.056，峰值 0.158，距上限 ρ=0.16 只剩 0.002。
2. **打开与否不能由查询长度解释**：非零组平均 12.6 字，零组 13.5 字，几乎相同；分界更像语气与指代明确度——「我家猫叫什么名字」归零，「先不说天气了，我家猫叫什么来着」开到位。
3. **零证据文本写得进去、取不出来**：无词法、无有效向量的内容（如纯 emoji）正常写入并留存原文，用完全相同的字符串检索返回空。这与数学规格一致，与「记了就该找得到」的直觉不一致。

## 一、口径

| 项 | 取值 |
|---|---|
| 样本 | 本机实例 25 轮对话的 `prepare_trace` |
| 参数 | 草案默认，ρ=0.16，未调 |
| 观测 | 每轮的 `gate.gamma`、查询原文、召回块数 |
| 召回上限 | 每轮 top-5 |

## 二、γ 的分布

| 统计量 | 值 |
|---|---|
| 样本 | 25 |
| γ>0 | 12（48%） |
| 均值 | 0.0559 |
| 中位数 | 0 |
| 最大 | 0.1582 |
| 最小非零 | 0.0346 |

十二个非零值：0.035 0.059 0.076 0.093 0.123 0.125 0.139 0.144 0.145 0.148 0.151 0.158。

两点值得注意：

- **召回块数在 25 轮里恒为 5**。所以「召回了几条」不携带信息，能区分的只有排序与 γ 本身。
- **分布是双峰的，不是连续的**。要么贴近 0，要么 0.1 以上；中间地带只有 0.035 和 0.059 两个点。这更像是门控把两类查询分开了，而不是在连续调节。

查询样例的分界很清楚：

| γ | 查询 |
|---|---|
| 0 | 我家猫叫什么名字？多大了？ |
| 0 | 你好呀 |
| 0 | 嗯…随便？ |
| 0.158 | 嘿，我小入机又回来哩 |
| 0.148 | 先不说天气了，我家猫叫什么来着 |
| 0.139 | 嘿嘿，可以 |

「我家猫叫什么名字」这类直问归零，「我小入机又回来哩」这类寒暄反而开满。门控读的似乎不是「要不要查记忆」，而是「这句话有多不像一个完整请求」。

## 三、零证据

复现步骤与结果：

```
tokenize("🎈🧩")                      -> []
append_document(doc_id="d1", raw="🎈🧩")  -> 写入成功，chunk 存在，vec 长度 0
retrieve(query="🎈🧩")                -> empty="no-evidence", retrieved=[]
```

对照：同一次写入里放一条正常文本（「我的猫叫年糕」），用「年糕」检索正常命中。所以不是写入链路坏了，是这一段本身就落在两条检索通道之外——BM25 没有词，向量没有方向。

原文一字不差地存着，用完全相同的字符串查，返回空。这不需要新机制才能修：原文精确匹配可以作为无证据时的兜底，代价是一次字符串包含检查。

## 四、能推出与不能推出的

能推出：

- 真实对话里门控不是罕见事件，把它当作「偶尔触发」会低估它的作用。
- 「召回数为 5」这类指标在这套实现里没有区分度，看它等于没看。
- 零证据是可达状态，不是理论边角。

不能推出：

- 不能推断 γ 与回答质量的关系。这里只记了 γ，没有对同批回答做评分。
- 25 轮来自一两次会话，query 风格单一，48% 不能当作总体比例。
- 双峰形态可能是样本量不足造成的，也可能真的是门控的两态行为，需要更多样本才能分辨。
