# 研究流程模块化（Draft）

> **方向已确定：研究流程采用模块化设计。** 本文记录当前设计、已有工程基础与待验证的细节；模块边界和编排方式仍可演进，不等同于一套要求每项任务照章执行的固定流程。现行研究原则见[研究流程](../rules/workflows/research.md)。

## 目标与边界

把研究工作拆成职责清楚、可以独立推进和复用的工作模块，再根据具体目标组合成研究流程。模块化要支持：

- **组合**：按问题需要连接不同工作模块，不预设唯一流水线。
- **嵌套**：一个模块内部可以调用或展开更小的探索、建模、验证流程。
- **循环与回退**：新证据可以使研究返回目标、假设或模型阶段，不必从头重做。
- **并行**：多个候选机制或实验分支可以独立推进，再依据证据和人的取舍剪枝。
- **切换协作方式**：同一流程可以在协同探索与 AI 自主深度推进之间切换，保持已有的决策边界和证据要求。

模块化不是为了让流程形式整齐，也不是把每项小任务都拆成许多步骤。目标是减少重复沟通和上下文损耗，让研究分支可组合、可复用、可回溯，并让不同工作能由合适的人或 Agent 独立完成。

本文讨论的是**研究工作流模块化**。它与 Agent Runtime 中的**软件模块化**有关联，但不是同一层概念：研究模块是可组合的研究活动；Runtime 模块是运行时接入的状态与行为组件。不能因为 Runtime 已有模块接口，就认为研究流程的模块定义和编排也已经完成。

## 研究工作模块

以下是当前适合识别和组合的工作职责，不是必须依次执行的固定阶段。一个模块可以由人、AI、脚本或代码工具完成。

1. **方向探索**：围绕希望观察的行为提出候选解释、机制和研究路径，暴露关键假设与分歧。
2. **问题形式化**：把方向转成可研究的问题，明确目标行为、输入条件、可观察量、成功与失败的判据。
3. **数学建模**：定义状态、输入、演化或学习规则、参数和假设，形成可分析、可计算的模型。
4. **性质分析**：检查模型产生目标行为的能力与边界，分析必要条件、稳定性、可达性及失败情形；不能证明的部分明确留给实验。
5. **数值实验**：通过可复现的实验、对照和参数扫描检验模型假设，记录数据、环境与局限。
6. **工程实现**：把已有依据的模型或机制接入 Runtime、插件或实验应用，验证接口、状态和运行行为。
7. **实际观察**：通过真实交互和运行 trace，观察机制是否改变了 Agent 的后续行为；区分内部状态变化、信息被提取和信息实际影响回答。
8. **综合与修正**：比较目标、模型、分析、实验和实际观察，决定保留、修改、排除或暂缓哪些方向，并把稳定成果沉淀下来。

「比较与选择」既可以是独立的决策活动，也可以发生在任何模块之间。技术性剪枝应有证据；涉及兴趣、价值偏好和真正目标的取舍由人参与。区分有依据地排除、暂缓和仍未确定，不把暂用假设悄悄升级为已确认决策。

## 流程组合方式

- **顺序组合**：例如问题形式化 → 建模 → 性质分析 → 数值实验 → 工程实现。
- **局部嵌套**：建模时发现关键假设不清，可以在建模流程内开启一次小型方向探索；实验设计也可以嵌套参数分析。
- **循环回退**：实验反例可以返回修改模型；实际交互发现问题可以返回研究目标或可观察量。
- **并行分支**：不同模型、参数或实现路径可以并行验证，最后依据共同的目标和证据比较。
- **按需裁剪**：小型工程问题可以直接实现和测试；已有充分结论的问题不必重复探索或建模。模块化不意味着每次都走完整路径。

现行规则中的默认研究路径仍然有效。模块化改变的是路径的组织方式：阶段可以拆分、复用、嵌套、并行和回退，而不是取消研究目标、数学分析、实验依据之间的关系。

## 模块设计原则

后续逐步明确模块契约时，至少应能回答：

- **职责**：这个模块解决什么问题，什么情况下值得调用？
- **输入**：需要哪些目标、假设、约束、已有结果和上下文？
- **输出**：产出什么可复用的结果或工件？哪些结论、证据和不确定性必须明确？
- **边界**：哪些判断可以自主完成，哪些需要人的价值选择或额外授权？
- **衔接**：后续模块如何使用输出？哪些前提变化会使已有结果需要重做？
- **完成条件**：何时可以结束、返回上层流程、开启分支或报告阻塞？

模块之间优先传递清晰的结果和必要依据，而不是无差别复制全部过程上下文。数学证明、实验数据、代码提交、运行 trace 和决策记录应保留各自来源；不能把假设、推断、实验观察和已证明结论混成同一种输出。

不预先规定统一的模块描述语言、流程 DSL、全局状态格式、审批机制或自动编排引擎。先让模块在实际研究中形成稳定边界，再决定哪些值得工具化。

## 当前演进方式

先用现有仓库和协作方式实践模块组合，不急于开发独立的研究工作流引擎：

- 以真实研究问题为单位，明确本次采用哪些工作模块、它们的依赖关系和预期输出。
- 用 Discussion 承载开放议题和方向碰撞；形成明确工作后用 Issue 跟踪；稳定结论再进入 Docs。无需把每个中间步骤都变成 GitHub 条目。
- 利用 Runtime、M1 模块和 extra 前端观察软件模块的协作边界、状态变化及行为 trace；不要把这些运行时能力直接等同于研究流程模块。
- 在流程中记录实际出现的重复劳动、上下文丢失、模块耦合、交接成本和返工原因，据此调整模块边界。
- 当某种组合方式反复出现且手工组织已成为明显负担时，再考虑标准化模块契约或实现编排工具。

## 待逐步明确的问题

这些问题讨论的是**如何设计和实现模块化**，不是是否采用模块化：

- 模块的最小粒度如何确定，怎样避免拆得过细？
- 模块之间以文档工件、结构化状态还是两者结合来传递结果？
- 如何表达依赖关系、并行分支、失败回退和局部重跑？
- 多个分支的证据如何汇总，同时保留相互矛盾的结果？
- 哪些模块可以由 AI 自主闭环，哪些节点必须保留人的价值判断？
- 什么时候手工编排已不足以支撑研究规模，值得开发专门工具？

设计取舍以实际研究收益为准：模块应当让工作更容易组合、接续和验证，而不是增加一层需要维护的流程负担。
